Document Agents: App Map

A one-page guide to where things live, so you know where to start the next time you change something.

What the app is

Upload one PDF, then ask questions that are answered only from that document; if the document does not contain the answer, it says "not found in this document." Four main pieces:

  • The site (React, port 4000): upload box, sidebar of saved conversations, chat.
  • The API (FastAPI, port 8000): receives the PDF and the questions.
  • The search (Chroma + a local embedding model): finds the 7 chunks of the PDF closest in meaning to a question.
  • Gemini: writes the answer from those chunks only, under a strict rule.

One action, end to end: asking "what does article 32 say"

The chunks searched here were prepared earlier, when the PDF was uploaded: POST /upload-pdf then chunking/chunking_pdf.py, then embedded and stored in Chroma.

A route through the code (reference route)

This is a suggested way to read the code. It is a reference, not a record of a tour you completed.

Stop 1: the question leaves the browser

Document_RAG_APP/src/components/Chat.jsx, search async function send. It adds your message to the screen, shows the waiting dots, and calls sendChat in Document_RAG_APP/src/api.js, which posts {question, session_id} to the API.

Stop 2: the API finds the evidence and asks Gemini

Document_RAG_API/main.py, search @app.post("/chat") (def chat). It loads or creates the conversation, saves your question first, then calls answer() in Document_RAG_API/rag/chat.py. There, retrieve() runs similarity_search for the top K chunks, and SYSTEM_PROMPT tells Gemini to use only those chunks or reply NOT_FOUND. The answer is saved with add_message in Document_RAG_API/sessions.py.

Stop 3: why the right chunk exists to be found

Document_RAG_API/chunking/chunking_pdf.py, search def _split_by_headings. At upload time the PDF is cut at its headings and every piece starts with a label such as "Article 32." That label is what lets a question mentioning "article 32" land on the right chunk.

A practice to reuse: measure before you change

What happened here. Questions like "what article 32 says" came back "not found in this document." Before changing anything, the cause was separated from the symptom: for "article 457" the answer was correct (the Constitution ends at Article 395, and the number 457 appears nowhere in the PDF), while for "article 32" the text existed but the search never returned it. Then four ways of chunking and three embedding models were compared on the same list of questions with known answers. Re-chunking alone did not help (about 5 of 14 found); a better model plus heading-aware chunks did (18 of 20). The same list also exposed a regression in one document style before it shipped.

Where it lives. Document_RAG_API/tests/eval_retrieval.py runs a list of questions against the loaded document and reports whether the answer text is in the top 7 chunks. The questions are in Document_RAG_API/tests/questions_constitution.json; the full record is in devpost/checklist.md under Revisions.

For another project. When an agent's output is wrong, write down 10-20 questions whose answers you already know, measure the current behavior, change one thing, and measure again. It keeps "this feels better" from standing in for evidence, and it tells you whether the problem is in finding the information or in using it.

Run the evaluation 
cd Document_RAG_API
.venv\Scripts\activate
python tests/eval_retrieval.py tests/questions_constitution.json

Upload the PDF in the app first; the script reads whatever document is currently loaded. It makes no Gemini calls.

Run it again

Start both servers (from the project folder) 
cd Document_RAG_API
.venv\Scripts\activate
uvicorn main:app --port 8000

cd Document_RAG_APP
npm run dev

Then open http://localhost:4000. First-time setup (virtual environment, pip install -r requirements.txt, your key in Document_RAG_API/.env) is in README.md.
